19 — CONNECTED STORAGE FABRIC, GIT FORGES & BRING-YOUR-OWN-CLOUD
===============================================================

PURPOSE

Poietek must never assume that every creator owns the same cloud service—or any
cloud account at all.

Storage is a user-controlled capability.

A project may live:
- entirely on the current device;
- on an internal or external drive;
- on a NAS/home server;
- in one cloud provider;
- across several cloud providers;
- in a Git repository for structured/versioned files;
- in object storage for large media;
- in a hybrid of all of the above.

CORE PRODUCT RULE

NO CLOUD IS REQUIRED.

Local creation, editing, saving, recording and export must remain available even
when the user never creates or connects a cloud-storage account.

------------------------------------------------------------------------------
1. STORAGE SETUP EXPERIENCE
------------------------------------------------------------------------------

On first use, present:

STORAGE MODE

[ Auto — Recommended ]
Poietek recommends locations based on what is available and connected.

[ Local Only ]
Keep all project data on this device unless I explicitly move or back it up.

[ Choose Locations ]
Set locations separately for projects, media, backups, models, cache and exports.

Auto is a RECOMMENDATION MODE, not permission to upload private work silently.

Before first use of any remote destination:
- show provider;
- show what will be uploaded;
- show visibility;
- show whether team members will have access;
- request explicit confirmation.

After a user approves a policy, Poietek can reuse it as their default.

------------------------------------------------------------------------------
2. DEFAULT RECOMMENDATION LOGIC
------------------------------------------------------------------------------

Always available baseline:

PROJECT STATE:
local durable database/project folder.

AUDIO/VIDEO WORKING MEDIA:
fast local storage.

CACHE / WAVEFORMS / PROXIES:
local only by default.

AUTOSAVE:
local.

If a connected provider exists, Poietek may RECOMMEND:

PROJECT BACKUP:
connected cloud drive or user-selected remote target.

BULK AUDIO/VIDEO BACKUP:
provider with large-object/resumable-upload capability.

STRUCTURED SOURCE / DEVICE PROFILES / SCRIPTS:
Git forge, if user intentionally enables it.

AI MODELS:
local model cache or a dedicated model hub/cache target.

IMPORTANT:
"Recommended" is computed from capability, not provider brand.

------------------------------------------------------------------------------
4. PROVIDER DETECTION
------------------------------------------------------------------------------

NATIVE DESKTOP/MOBILE CLIENT

May detect:
- mounted local volumes;
- removable drives;
- user-accessible mounted cloud folders;
- configured Poietek storage connectors;
- NAS/network mounts exposed by the OS.

WEB CLIENT

Must not pretend it can discover arbitrary applications installed on a device.

Web can know about:
- providers the user connected through OAuth;
- provider connectors enabled in Poietek;
- directories/files explicitly granted through browser APIs where supported;
- browser-local storage.

This distinction must be explicit.

7. STORAGE CLASSES
------------------------------------------------------------------------------

LOCAL WORKING STORAGE
Best for:
recording, realtime playback, current assets, cache.

PERSONAL CLOUD DRIVE
Best for:
backup, documents, project archives, optional media.

OBJECT STORAGE
Best for:
large immutable WAV/video/stem objects, team media and scalable remote assets.

GIT FORGE
Best for:
structured text, source code, schemas, presets, mappings, scripts, documentation,
issues and change review.

MODEL HUB
Best for:
AI models, model cards, datasets, adapters and evaluation assets.

APPLICATION BACKEND
Best for:
accounts, permissions, comments, collaboration metadata and notifications.

These are different jobs.

------------------------------------------------------------------------------
9. GITHUB / GIT FORGES
------------------------------------------------------------------------------

GitHub and similar services should be first-class Poietek integrations, but
Poietek must use them intelligently.

Excellent Git candidates:
- device profiles;
- MIDI maps;
- schemas;
- themes;
- presets represented as structured text;
- plugin/extension code;
- workflow scripts;
- documentation;
- ADRs;
- project manifests;
- release metadata;
- tutorial project structure;
- issue/feature proposals;
- test fixtures.

Poor default candidates:
- raw multitrack WAV;
- constantly changing video;
- render cache;
- huge proxies.

GitHub documents that Git LFS stores pointer files in the Git repository while
the actual large objects are managed separately, and GitHub imposes plan-based
per-file limits. Therefore Git LFS is an optional advanced bridge, not Poietek's
universal media store.

Poietek's internal versioning remains independent of Git.

------------------------------------------------------------------------------
11. HUGGING FACE ROLE
------------------------------------------------------------------------------

Hugging Face is primarily a model/data/application ecosystem, not merely a generic
cloud disk.

Current official Hub documentation describes:
- model repositories;
- dataset repositories;
- Spaces;
- Git-based versioning;
- Xet-backed large-file handling;
- newer non-versioned Storage Buckets for mutable object storage.

Potential Poietek uses:
- discover optional audio/MIR models;
- host Poietek-compatible open models;
- host model cards/evaluation results;
- publish research datasets when licensing permits;
- test AI demos in Spaces;
- maintain model versions;
- download user-selected models into a local cache.

Never automatically download or execute a model because it exists on a model hub.

13. REDUNDANCY
------------------------------------------------------------------------------

User-selectable policies:

WORKING
1 local copy.

SAFE
1 local + 1 verified backup.

IMPORTANT
1 local + 2 independent remote/removable copies.

ARCHIVE
2 verified durable copies; local working copy may be evicted only after user
permission and verification.

Poietek shows Storage Health:
Protected
At Risk
Missing
Uploading
Provider Offline
Needs Reauthorization

------------------------------------------------------------------------------
14. ASSET RESOLUTION
------------------------------------------------------------------------------

When opening an asset:

1. Look for verified local replica.
2. Look in local cache.
3. Look at mounted/removable storage.
4. Query preferred connected provider.
5. Query other authorized replicas.
6. If none available, show Missing Asset resolver.

Never replace missing content with a fake sound.

------------------------------------------------------------------------------
15. PROVIDER OUTAGE
------------------------------------------------------------------------------

If cloud provider becomes unavailable:
- project still opens;
- locally cached media works;
- new recordings remain local;
- sync operations queue;
- user receives a non-destructive warning.

If a remote-only asset is unavailable:
display placeholder and all known replicas.

------------------------------------------------------------------------------
16. TEAM ACCESS
------------------------------------------------------------------------------

Personal cloud does not automatically equal team storage.

Access classes:

PRIVATE_OWNER
TEAM_SHARED
PUBLIC
APP_MANAGED
EXTERNAL_SHARED_LINK

Before choosing a user's personal Drive/TeraBox file as team media, verify whether
collaborators can actually access it.

If not:
- copy/upload to an approved team destination; OR
- let collaborator provide another replica; OR
- keep project private to owner.

------------------------------------------------------------------------------
17. SECURITY / AUTHORIZATION
------------------------------------------------------------------------------

Tokens:
- stored in secure native credential storage where available;
- never in project JSON;
- never committed to Git.

Scopes:
request minimum required provider scope.

Disconnecting provider:
revokes or deletes local token according to provider capability.
Does NOT delete user files unless explicitly requested.

------------------------------------------------------------------------------
18. ENCRYPTED STORAGE
------------------------------------------------------------------------------

Optional application-level encryption for selected remote assets.

Encryption metadata:
algorithm
key reference
chunking
nonce/IV data
version

Keys remain separate from provider credentials.

This can allow a user to store encrypted project backups on a generic provider.

Do not implement custom cryptography casually; use mature libraries and security
review.

23. NEXTCLOUD / WEBDAV
------------------------------------------------------------------------------

Nextcloud's official developer documentation exposes WebDAV operations including
file/folder upload, download, move, copy, deletion, version handling and chunked
uploads.

This makes Nextcloud/WebDAV particularly valuable because users can attach:
- a hosted Nextcloud account;
- a self-hosted server;
- some compatible NAS/cloud systems.

A generic WebDAV adapter increases Poietek's independence from consumer-cloud
vendors.
