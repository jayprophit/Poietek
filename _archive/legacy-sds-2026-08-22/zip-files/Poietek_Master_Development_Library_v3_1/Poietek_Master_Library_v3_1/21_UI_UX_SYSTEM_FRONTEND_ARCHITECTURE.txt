21 — UI/UX SYSTEM, FRONTEND ARCHITECTURE & DESIGN STRUCTURE
==========================================================

PURPOSE

This document defines the complete front-end architecture for Poietek/SDS across:
- desktop;
- tablet;
- mobile;
- web;
- touch;
- mouse/keyboard;
- accessibility;
- multiple displays;
- beginner/pro modes.

The UI must remain one coherent product even though it contains many highly
specialized creative workspaces.

The front end is NOT the source of truth for project state.
React renders and edits canonical domain state through typed commands/services.

------------------------------------------------------------------------------
1. FRONTEND PRINCIPLES
------------------------------------------------------------------------------

1. DOMAIN FIRST
UI components never own durable project truth.

2. WORKSPACE BASED
Users move through purpose-built workspaces rather than one giant screen.

3. PROGRESSIVE DISCLOSURE
Advanced functionality exists without overwhelming beginners.

4. DEVICE RESPONSIVE
Phone, tablet, desktop and web render the same project with different layouts.

5. COMMAND DRIVEN
Buttons, shortcuts, MIDI controls, AI and menus invoke the same command layer.

6. ACCESSIBLE
Every core function has non-pointer access.

7. NON-DESTRUCTIVE
UI always exposes undo/history and version implications.

8. HONEST CAPABILITIES
Do not display controls for unavailable platform features as though they work.

------------------------------------------------------------------------------
2. FRONTEND LAYERS
------------------------------------------------------------------------------

Layer A — App Shell
Routing, top-level layout, account/session, platform capability context.

Layer B — Workspace Manager
Docking, tabs, windows, panels, splits, multi-monitor.

Layer C — Design System
Typography, spacing, controls, meters, waveform colors, focus, themes.

Layer D — Feature Workspaces
Arrangement, Mixer, Rack, Sampler, MIDI, Video, DJ, Rights, Community, etc.

Layer E — Inspectors
Contextual property editing.

Layer F — Command / Interaction Layer
Menus, shortcuts, gestures, MIDI, context commands.

Layer G — View Models
Derive UI-specific state from canonical project/domain state.

Layer H — Platform Adapters
Native dialogs, file pickers, windowing, share sheets, device permission UI.

17. FRONTEND STATE
------------------------------------------------------------------------------

Separate:

DOMAIN STATE
Canonical project.

SESSION STATE
Current unsaved UI operation, playback, recording session.

UI STATE
Selected objects, open panels, zoom, scroll.

PRESENCE STATE
Remote users/cursors.

DEVICE STATE
Connected MIDI/audio/controllers.

SYNC STATE
offline, queued, syncing, conflict.

Do not put all of these in one global store.

20. REACT PERFORMANCE RULES
------------------------------------------------------------------------------

Do not update the whole component tree at 60/120 Hz.

Use:
fine-grained subscriptions
canvas/WebGL for dense waveforms
off-main-thread analysis
requestAnimationFrame for visual meters
shared memory/ring buffers where platform architecture permits
virtualization for huge track/plugin lists

Audio engine never depends on React render timing.

------------------------------------------------------------------------------
22. WAVEFORM RENDERING
------------------------------------------------------------------------------

WaveformPeakCache provides multi-resolution peak data.

Frontend requests level based on zoom.

Very zoomed out:
summary peaks.

Zoomed in:
higher-resolution peaks.

Sample editor:
raw sample-level view only when necessary.

Large sessions must not decode full WAV repeatedly.
